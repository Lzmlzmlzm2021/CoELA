## 2. 方法定义与设计思想

V4 Harness 持续维护协作状态，为每个 Agent 提供相关的决策上下文，并在多个 Agent 提交提案后协调执行。各 Agent 的本地 LLM 自主选择高层计划，环境反馈再更新协作记忆。

三个核心模块是：

| 模块 | 保存或接受的信息 | 主要输出 |
|---|---|---|
| Persistent Coordination Memory（Blackboard） | 目标进展、资源控制、持续任务、承诺、Claim、执行证据和协作事件 | 当前协作状态及历史依据 |
| Agent-Specific Dashboard | 协作状态、Agent 身份、允许公开的信息范围 | 该 Agent 的紧凑决策上下文 |
| Coordination Governor | 各 Agent 的高层意图、底层动作提案及当前事实 | 通过或被调整的联合动作、裁决原因、任务与 Claim 更新 |

设计原则：

1. **策略选择由本地 LLM 完成。** Harness 提供信息与约束，模型决定选哪个目标、是否继续、何时运输或通信。
2. **事实与资源协调由规则维护。** 物体控制关系、已确认进展与资源竞争需要一致的执行语义。
3. **规则需要说明适用条件。** 物理资源互斥通常可迁移；整个房间是否应被预约、怎样判定探索完成，需要环境依据。
4. **软提示与硬约束分开。** Priority 和任务连续性影响呈现；Claim 与事实检查在执行阶段约束行为。
5. **任务记忆跨规划边界保留。** 临时计划被清除，不等于未完成的工作应该从记忆消失。
6. **信息权限可审计。** 中央存储中存在某条事实，不自动意味着所有 Agent 的 LLM 都能读取它。
7. **泛化效果通过实验验证。** 保持基线执行器、模型、预算和观察权限可比，再评估协作机制的贡献。

论文级概括：

> The harness maintains persistent coordination memory, projects agent-specific decision context for decentralized LLM planning, and reconciles action proposals through a coordination governor before environment execution.

## 3. Harness 与外围组件的边界

三个核心模块之外，还需要以下接口。

| 组件 | 职责 | 迁移方式 |
|---|---|---|
| Environment Adapter | 将已有环境观察和执行反馈转换成结构化事实 | 按 benchmark 重写 |
| Local Memory | 保存本人观察、物体记忆、地图与技能所需状态 | 优先保留基线实现 |
| Candidate Compiler | 根据本地状态、角色能力与动作定义生成高层候选 | 按 benchmark 重写或复用 |
| Local LLM Planner | 读取局部上下文、Dashboard、历史和候选，选一个高层计划 | 对接模型与输出解析 |
| Skill Executor | 将高层计划逐步转换成待执行的底层动作 | 优先保留基线实现 |
| Environment Executor | 执行治理后的联合动作，产生真实反馈 | 对接环境 step 或调度器 |

为了绘制简洁主图，可以把 Candidate Compiler 归入“决策支持接口”；实现时仍须区分：Dashboard 投影协作信息，候选生成主要依赖本地状态。不能将全部候选都写成从共享 Blackboard 生成。

## 4. Persistent Coordination Memory 保存什么

### 4.1 目标与已确认进展 [核心＋适配]

维护任务需求、已经确认完成的具体目标以及剩余需求。完成依据由官方环境或 evaluator 提供，Agent 的自然语言声明不能直接修改完成事实。

[TDW] 例如需要两个 apple 和一个 mouse，Evaluator 确认某个 apple ID 已交付后，剩余 apple 数量减一。

### 4.2 已知实体与信息来源 [核心＋适配]

记录实体身份、类型、允许使用的语义位置、观察者及更新时间。私有图像和导航地图仍可由各 Agent 本地维护。

中央账本内部可以持有双方信息，但 Dashboard 投影必须按权限筛选。本次讨论版共享承诺与协调事实，不自动把队友完整私有观察合并为本人的候选列表。

### 4.3 当前资源控制与 Payload [核心＋适配]

用物体视角查询“资源由谁控制”，用 Agent 视角查询“他持有哪些资源”。两者来自同一关系，不必作为两套独立事实维护。

[TDW] `physical_owners` 记录手持物体，以及被所持容器间接携带的物体；`self.payload` 和 `peer.payload` 是对该关系的投影。当前持有状态随新观察重建，并非永久累积。

### 4.4 持续任务与当前承诺 [核心]

持续任务记录 Agent 试图完成什么，以及其当前状态、负责人和中断原因。`active_task` 指向当前承诺的任务。

例如“取得 mouse 12”可以跨越多次导航动作，甚至跨越一次执行中断。短期 `plan` 被清除后，该任务仍可保留，供下一次规划考虑。

[TDW] 任务记录可能使用 `pending`、`in_progress`、`suspended`、`carried`、`completed`、`surplus` 等状态。迁移时按实际任务生命周期映射，避免照搬全部历史枚举。纯 V4 的拒绝恢复主要使用 `suspended`，不能把旧版本的定时 `blocked` 冷却当成默认机制。

### 4.5 Claim：当前有效的资源预约 [核心＋适配]

Commitment 表达“Agent 想完成什么”；Claim 表达“哪项资源暂由谁预约”。Claim 还不等于已经取得物理控制。

例如 Bob 已获准去抓 mouse 12，建立该物体的 Claim；真正拿起后，控制事实由 Physical Ownership 表达，该 Claim 可释放。

Claim 需要定义建立、刷新、完成释放、切换释放和过期规则。历史建立/释放记录进入事件日志，当前有效预约进入 Claim 表。

[TDW] 存在 object claim 与 room claim。房间预约用于协调探索，属于环境相关机制；其他 benchmark 若允许共同作业或会合，不能默认将整个区域设为排他资源。

### 4.6 Intent：计划的结构化表示 [核心＋适配]

由高层计划和动作提案提取 Agent、语义阶段、目标及执行状态。例如 `go grasp mouse 12` 可映射为 `acquire, target=12`。

Intent 连接 Planner、任务记录与 Governor。迁移时需稳定的实体 ID、任务 ID 和计划解析，不能依赖含糊字符串匹配。不同语义动作不一定都创建任务，例如通信通常不切换原有任务。

### 4.7 执行证据与协作事件 [核心＋适配]

执行证据描述一次实际动作的终态，例如有效性、成功或失败、动作 ID 和完成时间。底层转向成功不等于高层运输完成；语义进展应根据真实持有、环境确认交付或任务完成条件判断。

协作事件描述任务承诺、暂停、Claim 建立/释放、重新规划和恢复状态等变化。Governor 拒绝的提案也有原因记录，但必须与“实际执行后失败”区分。

[TDW] 部分拒绝信息保存在 `reviews`，Dashboard 读取其中与本人有关的近期记录。不要假设所有拒绝类型都以同名事件写入 `coordination_events`。

### 4.8 生命周期 [核心]

episode 级持续记忆不表示每个字段永久保留：目标账本跨 episode 内累积；持有关系是当前快照；Claim 有生命周期；事件历史有长度上限。新 episode 必须重置任务、Claim、证据去重状态和历史，防止跨任务污染。

## 5. Agent-Specific Dashboard 展示什么

Dashboard 从持续记忆中提取当前 Agent 需要的决策信息。它是一个视图，不是第二份独立的团队事实数据库。

| 信息 | 内容与用途 |
|---|---|
| 时间预算 | 当前原生时间与剩余预算，供模型判断执行节奏 |
| 团队进展 | 已确认完成数量和剩余目标 |
| 本人状态 | 当前 Payload、语义位置和高层任务 |
| 队友状态 | 允许公开的 Payload 和任务 Commitment |
| 任务记录 | 与本人有关的未完成工作、状态与优先级提示 |
| 有效 Claim | 其他 Agent 当前持有的物体预约 |
| 最近协调结果 | 近期任务事件、Claim 变化和本人被拒绝的原因 |
| 对话 | 近期允许保留的 Agent 消息 |
| 恢复提示 | 已启用的无进展检测结果和下一规划边界的限制 |

[TDW] 当前讨论实现中，`active_claims` 是其他 Agent 的有效物体 Claim；并不是历史 Claim，也不是基于距离挑选的相关子集。房间预约不应假定以相同字段完整展示。

[TDW] Dashboard 使用最近 12 条协调事件、最近 2 条本人相关 review 和最近 4 条 Agent 对话。这些数量是上下文预算配置，不是方法必须固定的常数。

代码里的 `[Memory Board]` 是 Dashboard 序列化后插入 Prompt 的文本标签。本文统一用 Persistent Coordination Memory 表示持续记忆，用 Dashboard 表示 LLM 读取的视图，避免名称混淆。

### 候选与排序 [适配＋配置]

候选主要由本人已知物体、持有状态、角色能力、探索状态和基本动作条件生成。“本地可选”不保证最终不存在跨 Agent 冲突，也不保证环境执行成功。

本次讨论版的决策支持包括：

- 活跃任务对应的已有候选可以前置，鼓励保持任务连续性；不新增或强制选择该候选。
- `suspended` 或受 loop guard 影响的任务不获得连续性排序优势。
- 固定任务 priority 可作为呈现提示保留。[TDW] 示例为运输 130、目标物体 100、容器 40、探索 20；不能据此声称所有候选都统一按这些数值重排。
- 共享交付点是单独开关，开启时可能影响运输候选是否可用；必须报告共享信息条件。
- Peer Claim 主要通过 Dashboard 告知模型，并在 Governor 阶段强制裁决；不能声称所有冲突候选都已预先删除。

### 刷新时机与读取时机 [核心]

Dashboard 可在每次 Coordinator step 更新；LLM 只在真实规划边界读取它。正在执行的高层计划通常由原执行器继续推进，不因 Dashboard 更新而自动调用 LLM。

## 6. Coordination Governor 如何处理提案

Governor 接受整批 Agent 提案及最新事实。逻辑上可以把任务同步与 Governor 归为同一治理模块；源代码中 `sync_tasks()` 与 `_review_and_govern()` 是先后调用的两个步骤。

### 6.1 将计划与任务记录关联 [核心]

根据结构化 Intent 找到对应持续任务：同一任务继续保留；切换任务时暂停旧任务、释放相关预约并记录新承诺。这个步骤只是同步模型选择与账本，任务成功仍由后续事实确认。

[TDW] 通信不自动切换任务；真实规划边界的显式 idle 可释放任务。迁移时要明确定义 wait/idle/release 各自语义，不能把执行器暂时清空 plan 误判为主动放弃。后续 Common V4 的等待与释放规则不同，见版本说明。

### 6.2 对同批资源申请进行裁决 [核心]

先收集双方提案，再检查它们是否竞争同一资源。已有效的 Claim 与真实控制关系必须纳入判断；没有既有预约时使用明确、可复现的仲裁规则。

例如双方都申请取得 mouse 12，仅允许一个申请通过；另一个获得冲突原因并重新规划。不能因为先调用了 Alice 的 LLM，就让 Bob 在同一批 Dashboard 中看到 Alice 新提交的选择。本次讨论版先为双方构造视图，再收集提案。

### 6.3 检查事实与能力边界 [核心＋适配]

检查范围包括资源所有权、有效预约、同批重复申请、实际容量、已确认任务事实以及已启用的区域预约或循环限制。

[TDW] 角色合法性部分由 `lm_agent` 在提交动作前检查，Governor 再执行协调与有限物理事实检查。因此“所有合法性检查都在 Governor 函数中完成”不准确。

Governor 通过表示满足所检查的约束，不能保证路径可达、没有碰撞或高层任务一定成功。距离、路线、容器收益和运输时机仍由本地规划及原技能实现处理。

### 6.4 拒绝与反馈 [核心＋适配]

冲突或违规提案被拒绝后，记录原因、清除需重新选择的短期计划、按规则暂停持续任务并释放对应 Claim。不要由规则直接替模型挑一个新目标。

[TDW] `_deny()` 的替代动作是按 Agent 编号选择的转向动作；部分其他分支使用等待。迁移时使用目标环境明确支持的安全动作，并计入原生预算，不能假设所有拒绝均为无成本等待。

### 6.5 无进展恢复 [配置]

本次讨论版检测连续真实规划边界上的相同动作身份，结合语义进展判断是否重复无效尝试。普通导航过程中多次移动不应直接算成多次 LLM 重试。

启用一次性 planning loop guard 后：保存原因，暂停相关任务并清除短期计划；下一次规划提示模型换一个动作；若模型仍提交完全相同的动作，由 Governor 拒绝该边界一次。候选本身不被永久删除，也不建立固定时长的目标冷却。

移植时必须说明哪些证据构成语义进展、何时算真实规划边界、阈值及开关。无法证明进展时，应在日志保留证据不足的状态，避免把底层成功当成任务完成。后续 Common V4 已改变这一硬恢复机制，不能混用。

## 7. 完整闭环与正确执行顺序

1. **接收观察。** 环境返回当前状态及上次真实执行反馈。
2. **更新记忆。** Adapter 整理事实，Blackboard 更新进展、持有、任务、Claim 和事件。
3. **构造双方 Dashboard。** 在本轮提案产生前，为每个 Agent 投影允许读取的协作上下文。
4. **各 Agent 推进。** 若当前底层动作仍 ongoing，则继续等待；若存在有效高层计划，执行器继续该计划；若进入规划边界，生成本地候选并调用 LLM 选择。
5. **生成底层提案。** Skill Executor 根据高层计划和局部状态计算下一条底层动作。此时尚未执行真实环境动作。
6. **整理 Intent 与任务。** 将高层计划关联到持续任务，更新承诺记录。
7. **联合治理。** Governor 检查整批提案、解决资源竞争，得到最终联合动作并记录裁决。
8. **真实执行。** 将最终动作交给环境 step 或原生调度器。
9. **反馈进入下一轮。** 持有变化、执行终态、官方进展和协作事件更新持续记忆。

必须保留“先生成待执行动作，再治理，再执行”的顺序。不能先让技能接口实际抓取物体，之后才检查 Claim。如果目标 benchmark 的技能 API 调用即执行，应增加准备/准入接口，将真实副作用放到准入之后。

### 高层计划何时重新选择

LLM 选择 `go grasp mouse 12` 后，`lm_agent` 可连续输出导航与抓取动作；模拟器执行底层动作，执行器判断高层计划是否结束。正常执行中不会反复调用 LLM。

高层计划完成、目标失效、原执行器发现新信息而中断、Governor 拒绝或恢复逻辑清除 plan 后，才出现新的规划边界。持续任务帮助模型判断原工作是否值得继续。

[TDW] V4 使用原版 CoELA 房间导航与探索。原 `gotoroom()` 在发现新物体时可以清除计划；因此高层计划未完成时也可能重新调用 LLM，这不是模型在每个导航步骤中规划。

## 8. 一个完整示例

以下为机制示意，不是实际实验轨迹，也不保证具体字段原样存在于所有适配器。

| 时刻 | 输入与处理 | 输出 |
|---|---|---|
| 观察 | Alice 与 Bob 都在自己的合法观察中知道 mouse 12；尚无 Claim | 本地各自可生成抓取候选 |
| Memory → Dashboard | 更新双方状态，构造同批视图 | 两人都看到尚无有效物体预约 |
| Planner | 两个本地 LLM 都选择取得 mouse 12 | 两个高层计划 |
| Skill | 根据各自位置计算下一条导航/抓取动作 | 两个尚未执行的底层提案 |
| 任务同步 | 将提案关联到 mouse 12 对应任务 | 临时更新任务承诺，等待裁决 |
| Governor | 发现同批竞争；假设本轮 Bob 获胜 | Bob 获得 Claim，Alice 被拒绝并收到原因 |
| 环境执行 | Bob 执行批准动作；Alice 执行拒绝分支的替代动作 | 新状态和真实动作反馈 |
| 下一规划边界 | Alice 读取 Bob 的承诺、有效 Claim 和本人拒绝原因 | Alice 的 LLM 可选择其他目标；规则不代选 |
| 后续执行 | Bob 的现有计划持续推进 | 导航步骤不反复调用 LLM |
| 拿起成功 | 观察证实 Bob 持有 mouse 12 | 更新 Physical Ownership，释放物体 Claim，刷新任务状态 |

实现时要检查共享任务 ID 的竞争更新：被拒绝者的状态变更不能意外清除获胜者的承诺或资源保护。这是移植必须验证的边界，不能仅凭三模块架构认为已经正确处理。

## 9. 跨 Benchmark 的最小接口契约

以下是迁移设计接口，不是要求源代码存在同名函数。

| 接口 | 输入 | 输出与要求 |
|---|---|---|
| `observe_facts` | 原生观察、执行反馈、官方进展 | 有来源的事实；遵守公开权限 |
| `update_memory` | 上轮 Memory、新事实 | 更新后的状态；完成证据去重 |
| `project_dashboard` | Memory、Agent 身份、可见性策略 | 本人的紧凑上下文；屏蔽私有信息 |
| `generate_candidates` | 本地记忆、能力、任务条件 | 稳定可解析的高层候选 |
| `select_plan` | 候选、Dashboard、局部历史 | 模型选中的候选或明确解析失败 |
| `skill_step` | 当前计划、本地状态 | 待执行底层动作、ongoing 或计划结束；不提前执行真实动作 |
| `compile_intent` | 高层计划、动作提案 | 稳定任务 ID、资源 ID、语义阶段 |
| `govern` | 整批 Intent、动作提案、Memory | 最终联合动作、裁决记录及资源更新 |
| `environment_step` | 治理后的动作 | 原生反馈；保留真实执行并发与成本 |
| `task_progress` | 前后事实、任务定义、官方结果 | 可解释的语义进展或证据不足 |
| `reset_episode` | 新任务与 Agent 配置 | 清空上一 episode 的全部协议状态 |

部署前明确四项环境条件：资源是否排他及容量；高层动作是否异步；谁能看到哪些信息；完成标准与原生预算。原生环境若每步只允许一个动作，就不能通过 Harness 人为获得并行执行能力。

## 11. 部署顺序与验收

建议按以下顺序实施：

1. 固定源 V4 版本与目标 benchmark 基线，记录模型、预算和观察权限。
2. 梳理原 Agent 从选高层动作到环境执行的调用链，定位安全的治理插入点。
3. 实现事实、能力、资源、任务 ID 和完成证据适配。
4. 接入持续记忆与 Dashboard；检查信息来源和权限。
5. 保留本地候选与技能，接入规划边界、Intent、任务同步和 Governor。
6. 明确 priority、连续性提示、room claim、共享信息和 loop guard 的配置，记录与源版差异。
7. 用短任务验证实际执行闭环与日志，然后进行基线对照评测。

至少验证：

- 双方同批请求同一排他资源时仅一方通过，失败者不会改坏胜者状态。
- 已开始的技能在队友多次规划期间仍受到正确资源保护。
- 正常高层技能内部不会被误计为多次 LLM 重规划。
- 中断后原任务保留，模型能读到中断或拒绝原因。
- 通信、等待、切换和释放的任务语义符合所选版本。
- 底层成功、语义进展和官方计分分别记录；反馈去重不会重复加分。
- 私有感知不会因中央 Memory 的存在自动公开。
- Claim 释放、过期、实际持有和新 episode 重置相互一致。
- 所有等待、通信、拒绝替代动作遵守环境成本。
- 官方成功率/完成率、步数或时间、LLM 调用量、冲突拒绝、重规划和失败结果均可从日志核对。

这份清单是部署验收要求，不声称现有源分支已通过全部边界测试。
